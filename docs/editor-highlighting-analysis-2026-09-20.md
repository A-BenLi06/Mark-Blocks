# 编辑区高亮丢失与颜色污染分析

## 后续修复记录

滚动补色修正：焦点保护此前也挡住了新视口的着色。现在两端的滚动完成事件可请求有焦点时的视口补色，继续等待输入静默并遵守分批预算。此路径排除当前光标/选区涉及的完整段落，不重设插入点格式；保护区边界计入缓存匹配，失焦时失效缓存以补齐被跳过区域。新增四项保护区与离屏光标的回归检查，总计 58 项及 1000 组随机用例通过，两端 Release 构建通过。仍需真机验证滚动时的 IME、原生布局与撤销行为。

已将着色拆为完整颜色分段计算和可续执行的原生应用两步。正则失败发生在写格式之前；8ms 预算耗尽保留分段游标，以 33ms 计时器继续，全部完成后才标记缓存有效。不再先刷白整个可见区，也不再用编辑前的旧绝对下标清除另一区域。编辑、文档替换和撤销均失效缓存；原生写入/收尾失败清空状态。搜索改用原生选区，不写黄色背景或黑色前景。修正根元素 Default 主题回退；焦点进入时只恢复折叠插入点的正文色，保留重做分支。

仍保留编辑焦点期间暂停重着色的 IME 保护，故新增文本可能直到失焦才补色；CanRedo 为真时仍延后着色。此次没有宣称消除全部原生格式继承情况，也没有把 Windows 8.1 的输入空闲视作可靠的组合结束事件。离屏区域不主动清色，主题变化后在该区域下次进入可见范围并允许着色时更新。

新增颜色分段完整覆盖、标记/正文区分、密集文本、预算退出后续跑、不重复应用等回归检查。测试不模拟 WinRT 原生格式、IME 或撤销栈；仍需在目标机复验中文输入、选区替换、主题切换及撤销重做。

## 结论与证据边界

左侧是 RichEditBox 原生字符格式着色，与右侧 WebView 的 Markdown 渲染是两条路径。代码能确认高亮调度、缓存和格式所有权存在缺陷；尚未在目标机捕获“全部变灰”的具体事件序列，不能把全部现象归于单一原因。本轮记录分析，不修改着色行为。

## 1. 焦点保护造成高亮长期缺失（已确认）

MarkdownHighlightingHelper.HighlightVisible 在编辑器持有焦点时直接返回，Windows/Phone 页面也在 SyntaxTimer_Tick 和 HighlightMarkdownSyntax 中阻止着色，直到 LostFocus。该策略是上一轮为避开 Windows 8.1 拼音组合输入期间的格式写入而加入的保守降级。

结果是：持续编辑或滚动时，新文本、新出现的区域不补色；切换文档时如果编辑器仍有焦点，首次着色也可能被跳过。深色主题的正文色本来就是白色，因此表现为“变成纯白”。目前只给 Markdown 标记着灰色，并不是完整多色语法高亮；普通正文保持白色本身不是错误。

## 2. 不完整着色被缓存成完整结果（已确认）

ApplySyntaxRanges 使用 8ms 软预算，超时直接 return；调用方不接收完成状态，仍设置 currentRange.Text、颜色和 IsValid=true。下一次若文本、范围和主题颜色相同，会命中缓存直接退出。

此前已把可见区域全部重置为正文色，预算退出却只恢复了部分标记颜色，因此部分高亮会永久缺失，直至其他变化打破缓存。正则超时或原生格式写入异常则可能发生在颜色已经被改写之后，catch 返回的 previousRange 也不能代表当前原生格式状态。

## 3. 灰色字符格式继承（高概率机制，需真机确认范围）

高亮直接给标记范围写入 ForegroundColor=灰色。RichEdit 的插入文字可能继承邻近范围或插入点格式。正文颜色纠正位于高亮函数内，仅在折叠选区时执行；新增的焦点保护会阻止这条纠正路径在编辑过程中运行。

因此在灰色标记附近开始输入、删除标记后续写或换行时，灰色可能延续到正文。当前实现没有专门的灰色全文写入路径，不能仅凭源码断言它解释了整份文档变灰；还需观察选区、撤销和原生格式继承的具体状态。不要通过给整个当前选区强制设正文色来修复，这会再次破坏选区高亮和 IME。

## 4. 撤销和缓存缺乏统一失效规则（已确认）

格式操作被放入 BeginUndoGroup/EndUndoGroup，仍可能进入原生撤销历史。页面循环跳过仅格式变化的撤销项，随后把 _pendingSyntaxRefresh 清为 false；并未统一失效 _highlightRange。高亮器还会在 CanRedo() 为 true 时停止工作，以保护重做历史。

所以撤销后原生颜色可能改变，而文本缓存未反映格式变化；重做分支存在时不会自动修复。这也解释了问题为何可能随撤销/重做间歇出现。

## 5. 搜索与语法高亮争用前景色（已确认）

Windows 和 Phone 的 FindInEditor 把当前匹配写为黄色背景、黑色前景；清除旧匹配时只恢复透明背景，没有恢复原前景，也没有失效高亮缓存。深色主题上旧匹配可能变暗或不可见。这是独立缺陷，不应误判为灰色全文现象的唯一根因。

## 6. 范围与主题判断的边界

缓存保存的是绝对字符下标，编辑后未按增删调整，后续清理旧范围可能清除不再属于旧着色范围的颜色。可见文本从中段截取后使用行首正则，也不能完整判断代码围栏等跨区语义。

IsDarkTheme 只判断根元素 RequestedTheme 是否恰好为 Dark；如果为 Default，没有继续解析应用主题。这是潜在主题判断缺陷，是否能触发取决于项目实际主题设置路径。

## 建议修复顺序

1. 着色器返回完成/未完成/跳过状态。预算退出或异常不能生成“完整缓存”；在安全时机重试，并给每轮工作设置明确边界。
2. 合并语法、搜索、主题和撤销的格式失效规则。搜索优先使用选区表达匹配，不永久写黑色；确需背景标记时，要保存和恢复原格式并管理文档切换。
3. 先计算语法标记范围，再应用最小差量；取消“先将整个可见区刷为正文色，再逐项补回”的方式，降低中断后大面积失色的风险。
4. 设计明确的编辑中着色策略。Windows 8.1 没有这里需要的 RichEditBox 组合输入生命周期事件；仅延长防抖不能可靠识别候选框状态。保守延迟着色和可靠实时着色应作为不同方案评估，不能用任意停顿时间声称 IME 已结束。
5. 用目标机记录实际格式写入耗时、完成状态和触发源，复验标记后中文输入、换行、删除标记、长时间选词、滚动、切文档、搜索、撤销重做、主题切换。日志只需事件与范围长度，不记录正文。

保留 RichEditBox + WebView 可以修正以上大部分问题；当前证据不足以支持因此重写输入引擎。
