# 文件打开链路复盘

## 结论与证据

用户样本 HK&SZ.md 位于指定目录下的 Travel 子目录。仅在本机读取和生成被 Git 忽略的测试产物，没有修改原文件或抓取文档中的在线资源。

样本为 71,724 字节、53,510 字符、1,133 行；解析后有 487 个顶层内容块、249 张图片（包括原始 HTML 图片），HTML 约 150,196 字符。不需要代码、公式或图表库。相对于文本容量，它更接近图片密集文档。

独立 .NET 测试运行的读取耗时约 10 ms，冷解析 49–53 ms，随后两次约 5–8 ms。该环境不是应用的 .NET Native/WinRT 运行环境，不能据此声称目标设备打开只需这些时间，但没有证据支持优先重写 Markdown 解析器或文件读取算法。

代码确认的额外工作：ActiveDocument 通知已经填充编辑器、发起后台解析，OnNavigatedTo 又重复填充、请求解析和全局格式设置；还会在解析未完成时打开空/旧预览骨架，之后通过 InvokeScript 再传整篇 Base64 内容。截图则确认资源解析器对不在图片白名单中的路径主动抛出 FileNotFoundException；调试器开启 thrown 中断时，这会直接暂停应用。截图未提供具体 URI，不能断言一定是 favicon。

## 本次实现

- Windows/Phone 导航只在尚未同步当前文档时填充编辑器。Windows 去掉初次重复格式设置及提前打开空骨架。
- 首次内容在 NavigationCompleted 后由原生端提交，通过补丁返回 ok 确认后才记录块快照。已撤回随导航脚本提交正文的尝试；它在目标机出现静止不显示的问题，不能仅凭导航已发送就跳过首次内容提交。
- 初始化仍用原有 Base64 加惰性 DOM 片段解析，保留更新时的 HTML script 不执行语义；不直接把原始 Markdown HTML 拼入页面顶层。
- 先安装近视口处理器，再调度图片和复杂块，避免初始化走旧的全 DOM 扫描逻辑。网络图片不作为正文显示的前置条件。
- 本地资源解析器明确支持 KaTeX 包内字体。未知路径返回空原生流并记录路径，不主动制造文件不存在异常；不扩大到任意本地文件访问。缓存图片仍有自己的命名白名单和原网址回退。
- 导航失败不再标记 WebView 已就绪。Windows Debug 输出分别记录读取/规范化、RichEditBox 填充/格式化、后台解析耗时，供目标机定位剩余瓶颈。

保留 RichEditBox + WebView 是当前证据下代价和收益更合理的选择。RichEditBox 的 SetText 仍需 UI 线程执行；不能用 Task.Run 包裹来伪装异步，也不按段追加制造复杂撤销/输入竞态。若真正数 MB 文档仍慢，先查看原生填充时间，再评估分阶段编辑状态与渲染块虚拟化。完整的 XAML Markdown 引擎不会自动解决 RichEditBox 填充成本，且会引入排版和功能兼容成本。

## 验证与限制

目标机再次反馈后，撤回上轮 `__mdPreviewReady` 唤醒与布局轮询。当前恢复明确的“导航完成 → 原生端提交内容 → 收到补丁成功回执”顺序。同时修复图片回填因位置变化被跳过后仍保持已激活的状态，并在图片解码改变布局后主动调度近屏检查。目标机原始现象尚待验证，不把这些代码修正称为已确认的唯一根因。

Windows x86 / Phone ARM Release 编译通过；纯托管回归和浏览器回归通过。测试按原生端导航完成后提交首个补丁的顺序运行，并确认图片回填被跳过后仍可再次激活。

此前随导航提交正文的 Edge 实验显示全部 487 个内容块，单次记录约 464 ms（该路径现已撤回，此数字不能作为当前版本性能）；300 ms 后只请求近屏的 12 张图片，249 张图片没有同时启动。测试阻止所有 HTTP(S)，用模拟原生桥接收集请求，不下载私人文档引用的资源。此数值是浏览器测试，不是旧 WebView 的原生首帧或端到端耗时，也不是前后对比加速比。

复现：先运行 PerformanceRegression 的 `--benchmark <本地 Markdown 路径>`，再运行 `preview-open-benchmark.cjs`（使用现有 PLAYWRIGHT_MODULE 环境）。真实设备仍需核对冷启动、重开、切换标签、输入后切换、图片命中/未命中缓存，以及包含公式字体的文档。若仍出现长黑屏，使用上述 Debug 分段日志与具体 URI 定位，不再盲目加节流。
